# Dashboard UI guidelines

**Branding note:** Use soft digital blues, cyans, and light polygon-inspired accents inspired by Porygon.

## Component set

The dashboard components in `web/src/components/` are PoryMCP's own MIT code
over Headless UI 2.x and Tailwind v4. Nothing in that directory comes from a
kit, and a new component is written here, never imported from one. Third-party
notices for the packages the bundle is built from are in [`NOTICE`](../NOTICE).

- **`primitives.tsx`** is the only home of the shared recipes: `focusRing`
  (the keyboard focus outline), `controlFrame` and `controlField` (the chrome
  of a text control), `optionField` (the checkbox/radio row grid),
  `TouchTarget` (the 44px hit area) and `errorLine` (the pink line a page or a
  dialog reports a failure in). A component or a page composes these by name;
  none carries a private copy.
- **`--color-focus`** in `web/src/styles/tailwind.css` is the one spelling of
  the focus colour (`outline-focus`, `ring-focus`, `bg-focus`). Brand surfaces
  keep literal `cyan-*` until PORM-9 moves them onto `--color-brand*`.
- The **authoritative export list** is `grep '^export' web/src/components/*.tsx`;
  it is not transcribed here.
- The **`data-slot` vocabulary** is public API: `icon` (Heroicons emit it
  themselves; parents size and colour icons off it), `control`, `label`,
  `description`, `legend`, `text`, `field`, `section`. Every Heroicon
  rendered *inside* a component is sized explicitly: by its own class, or,
  for the drawer's open/close glyphs, by `NavbarItem`'s `data-slot=icon` rule,
  exactly as the pages' icons are.
- **`--gutter`** is a cross-component contract: pages set it on `Table`
  (negative outer margin, inner padding, and the first/last cell padding below
  `sm`); `Dialog` sets its own on its panel.
- `help-disclosure.tsx` is the worked example of the house pattern: a plain
  exported function, `clsx` with the caller's `className` first, Headless UI
  for behaviour, a Heroicon for the glyph, `dark:` pairs inline.
- Dark mode follows `prefers-color-scheme`; there is no toggle.
- Behaviours that are invisible at the call site and must survive any rewrite:
  `Link` wraps `next/link` in Headless `DataInteractive` (the source of
  `data-focus` on anchors); `SidebarItem` with `href` is a Headless
  `CloseButton` (what closes the mobile drawer on navigate);
  `SidebarSection` scopes the current-page indicator in a `LayoutGroup`
  keyed on `useId()` because the sidebar is mounted twice below `lg`; a linked
  `TableRow` has exactly one tab stop.
- Known accessibility gaps carried over from the original set, tracked in
  PORM-123 together with
  the deferred improvements (`prefers-reduced-motion`, 48px touch targets):
  linked table rows have no accessible name, Logs rows are not
  keyboard-reachable, `Input`/`Textarea` show no focus outline below `sm`,
  nav items set `data-current` but not `aria-current`, and the mobile drawer
  has no accessible name.

Use the **Application Shell** (sidebar layout) as the main frame.

No dashboard route may end in `/mcp` at any depth: the proxy owns
`/{virtual_key_id}/mcp` and `/{virtual_key_id}/{upstream_slug}/mcp`, and any
path of that shape reaches it rather than the SPA.

## Pages
1. **Dashboard / Overview**
   - Stats cards (active virtual keys, total calls today, upstreams, error rate).
     Each card shows `LOADING` from `web/src/lib/placeholder.ts` (a non-breaking
     space, so the card keeps its height) until `/stats` answers. Table cells
     elsewhere show `ABSENT` (`None`) for a value the row will never have.
   - A credential notice above the stats, driven by the live counts on
     `/stats` (never by `/health`, whose verdict is a boot fact): when stored
     credentials cannot be read with the current `ENCRYPTION_KEY` it names the
     count and the fix and links to Upstreams; when a rotation is unfinished
     (`upstreams_under_previous_key > 0`) it says to run `porymcp rekey`.
     Nothing renders while stats are loading, and no server string is rendered:
     the copy is the dashboard's own. A second notice sharing this card
     recipe should extract a component rather than copy it again.
   - Recent activity feed

2. **Upstreams**
   - Table: Name | Slug | URL | Kind | Auth | Status | Actions (Connect
     on an OAuth row, then Tools or Test, Edit, Delete). The Kind cell reads
     `MCP server` or `HTTP API` (PORM-146), the same labels as the Add
     dialog's Kind radio, with the `Unsupported` badge beside `MCP server` on
     a row stored with transport `sse`. The page copy reads "Real MCP servers
     and HTTP APIs. Credentials are encrypted at rest and never shown again."
     and the empty state "No upstreams yet. Add the first MCP server or HTTP
     API." The Status cell holds two
     facts, stacked: the Enabled/Disabled badge someone set, and under it the
     last test as a dot and a word: `Not tested`, `Passed 3m ago`, `Failed 2h
     ago`.
   - The Auth cell says what the stored credential is worth (`auth_status`,
     PORM-52): the auth type, then `· set` when PoryMCP can use it, a pink
     `Unreadable` badge when no configured key opens it (the encryption key
     changed, so the fix is a key), a pink `Incomplete` badge when the stored
     value is empty or unusable for its auth type (the fix is the credential),
     and nothing for `none`. On an OAuth row (PORM-139) `unreadable` reads
     `· Not connected` as plain text (nothing is wrong with the setup; the
     fix is Connect), `expired` is an amber `Expired` badge (the badge rule
     gives amber to "held or expired", as an expired virtual key gets, and
     pink to a broken setup; the fix is Connect again), and `ok` with no
     refresh token reads `· set until <time>`. A refresh that fails for a
     reason other than the vendor refusing it leaves the cell at `set`; the
     Logs row reads `credential refresh failed`. The rule lives in
     `web/src/lib/upstream-auth.ts`; an `auth_status` value the dashboard
     does not know renders no badge. So a `Failed` dot in the Status cell has
     its cause one column to the left.
   - Connect (PORM-139) is a row action on every OAuth row, `Reconnect` once
     a token set is stored. It asks the server for the vendor's sign-in URL
     (the button reads `Connecting…` meanwhile and every Connect is held) and
     takes the current tab there: the admin key lives in this tab's session
     storage and survives the round trip, and the callback page brings the
     operator straight back to this list, where the row reads `set`. A
     refusal renders as an announced line above the table. In the Edit
     dialog an OAuth row shows the state under Auth type ("Not connected.
     Press Connect on the upstream's row to sign in to the vendor.",
     "Connected. PoryMCP renews the access token before it expires.", the
     expired and no-refresh-token sentences), a "Did the vendor give you a
     client ID?" disclosure holding the redirect URL to allow at the vendor
     (read from the client metadata document, with Copy), the optional Client
     ID and Client secret boxes (blank means keep; a secret without an ID
     holds Save with "Enter the client ID that goes with this secret.") and
     a "Register PoryMCP with the vendor instead of publishing its client
     document" checkbox that the next Connect on the row sends; the
     disclosure starts open when a supplied client is stored. At the foot of
     the dialog a Disconnect section: an outline `Disconnect` button on a
     connected row ("Asks the vendor to revoke the token, then removes it
     from PoryMCP. Calls through this upstream fail until it is connected
     again.") or `Remove client ID` on a row holding only a client, each
     behind an Alert confirm, and a status line afterwards saying what the
     vendor did. Choosing OAuth in the Add dialog says "After Create, press
     Connect on the upstream's row to sign in to the vendor." and disables
     Discover tools with "Discovery needs a token. Create the upstream,
     connect it, then use Tools on its row." A URL change on a connected OAuth
     row says "Saving a new URL disconnects this upstream. Connect it again
     afterwards."
   - “Add Upstream” button opens a modal or slide-over form. The Slug field previews
     what the server will derive from the Name and stays in sync until you edit
     it; leave it alone and the server derives, de-duplicates and skips reserved
     words.
   - **Kind** (PORM-146) is the first fieldset of the Add dialog: a radio
     group of `MCP server` and `HTTP API`, each with one sentence. Choosing
     HTTP API relabels the URL field **Base URL** with the help "Requests to
     the key's endpoint are sent here with the stored credential. The path
     after /api/ is appended.", hides Transport, adds a **Test path** input
     (`dir="ltr"`, at most 256 characters; help "A path the connection test
     requests, such as /user. Left empty, the base URL is tested."), leaves
     OAuth out of the Auth type select and, when OAuth was chosen, resets the
     auth type to None and clears the client boxes
     (`applyKindChange` in `web/src/lib/upstream-form.ts`). The disclosure
     under the URL then reads "What base URL should I use?": **the API's
     root** (a caller's path is added after it: for
     `https://api.example.com/v1/user`, enter `https://api.example.com/v1`),
     the redirect paragraph unchanged, and **check it before you save** (Test
     sends one GET with these settings and shows the status). In Edit, Kind is
     not an input: the description line reads "Slug: {slug}. Kind: {label}.
     Both are fixed once the upstream is created.", Transport shows on MCP
     rows only and Test path on HTTP API rows only, and the third disclosure
     paragraph reads **check it after you save** (Test on the row sends one GET
     with the saved settings and the stored credential). A change of kind
     discards the discovery panel like any other connection field.
   - The slug is fixed once the upstream is created, so it is not editable: it
     is the path segment of every per-member client URL and half of every tool
     identity written against that upstream. The field's help text says so:
     “Used in URLs and in tool names on the group endpoint. Fixed once the
     upstream is created.”
   - Edit on a row opens the same dialog pre-filled from the row and saves with
     `PATCH /upstreams/{id}`. The body carries only the fields that changed,
     with one exception: `auth_type: none` goes for a None row that still
     holds a stored value when the operator ticks Remove the stored value.
     Never `slug` (the dialog shows it in its description line and has no
     input for it), and never `auth_config` unless a credential was typed. The
     credential boxes start empty and blank means keep. When the stored
     credential reads, the help text names the header it sends; when it does
     not (`Unreadable`, `Incomplete`) the help text says it has to be entered
     again, header name included. A change of auth type, or of the header name
     on a header-shaped type, makes the credential required, because the name
     is sealed inside it; the header name itself is required whenever a
     credential is being sent, so an empty one never reaches the server.
     Choosing None on a row that holds a credential says saving removes it and
     it cannot be recovered. A None row that still holds a stored value (a
     credential switched to None by an earlier build, the empty object earlier
     builds sealed for a blank box, or a credential a client sent alone to a
     None row) shows a Remove the stored value
     checkbox beside Enabled; ticking it and saving sends `auth_type: none`,
     which removes the value. A changed URL on a working credential says PoryMCP will send that
     credential to the new address. The Discover tools block is create-only:
     from an edit the payload route would probe with whatever the box holds,
     and Tools on the row tests the saved upstream with its stored credential.
     The row is replaced from the PATCH response, which already carries the
     reset last test, so no second request runs.
   - Delete asks through `Alert`, the shape the Virtual keys page uses. A `409`
     (still held by a group or targeted by a key) keeps the Alert open with the
     reason; a `404` reloads the list. The rules behind the dialog live in
     `web/src/lib/upstream-form.ts` and `web/src/lib/edit-error.ts`, with tests.
   - In the Add dialog the URL field carries no help text of its own (in the
     Edit dialog it carries up to two lines: the credential-follows-the-URL
     line and the plain-http note); under it sits one line,
     “What URL should I use?”, a `HelpDisclosure` that opens on click, Enter or
     Space and on nothing else. It answers in three paragraphs: **the MCP
     endpoint, not the home page** (the address usually ends in `/mcp`); **the
     final address**: PoryMCP sends the credential to exactly the URL you enter
     and never follows a redirect, so an `http://` address that redirects to
     `https://`, or a path missing its trailing slash, fails with `502` and a
     log entry reading “upstream redirected to …”; and **check it before you
     save**: Discover tools connects with these settings and lists what the
     server offers. In the Edit dialog that third paragraph reads **check it
     after you save**: Tools on the row connects with the saved settings and the
     stored credential, which the browser cannot send from there.
   - Each row has a **Tools** action beside Edit and Delete. It opens a “Tools” dialog
     that calls the upstream there and then and lists what it offers: server
     name and version, latency, the protocol line (the version, and whether the
     server is stateless or uses the handshake), the tool count, and
     every tool by the name the server publishes and, beneath it, by the name a
     group endpoint gives it (`{slug}__{tool}`), with a Copy button that copies
     that second form, the one an allow rule has to be written in. A Refresh
     button re-runs it. The tool list is not stored and is gone when the dialog
     closes, but the run itself is: every press records, on the upstream's row,
     when it ran and whether it passed, and the panel says so. The Status cell
     in the table carries that result (a dot and a word under the Enabled
     badge: `Not tested`, `Passed 3m ago`, `Failed 2h ago`), so a misconfigured
     upstream is visible without opening the dialog. The press updates the row
     itself: the table is re-read when the run settles, so the dot changes
     without a reload even if the dialog was closed while the handshake was
     still running, and it reads `Passed just now` or `Failed just now` for the
     first minute. The relative label is computed when the list arrives rather
     than on a timer, so it does not tick on a page left open; the exact instant
     is in the cell's `<time>`. Changing an upstream's URL, transport, auth type
     or credential resets it to `Not tested`: a green dot against a connection
     nobody has tried is worse than no dot. The row is not clickable and does
     not expand: discovery is an authenticated outbound call to an
     operator-supplied URL, and now also a write to that upstream's row, so it
     happens only on a deliberate press. A **Load tools** press in a group or
     virtual key dialog is the same call, once per member of the target, and
     records the same last test on each member it reached: a member that is
     down turns its dot red from there too, and the dialog says so before the
     press.
   - On an HTTP API row the action reads **Test** instead of Tools and opens a
     “Test” dialog (PORM-146) on the same panel, branched on the row's kind:
     "Connecting to <host>…" while it runs; on an answer a description list
     of Status (the upstream's HTTP status, only when it answered), Request
     (`GET /user`, from `test_path`, or `GET /` for the base) and Latency,
     with the failure sentence in pink above it on a non-2xx; on a transport
     failure the sentence alone. No catalogue block and no "Which name do I
     use?" disclosure, because there are no tools. The recorded-run note
     reads "PoryMCP records when this upstream was last tested and whether it
     passed. The Status column shows it." and the dialog's button reads
     **Test again** / **Testing…**. The Add dialog's foot button reads
     **Test** / **Testing…** on HTTP API with the caption "Sends one GET to
     the base URL and test path using these credentials, and shows the
     status. Nothing is saved, and this check is not recorded as a test.",
     and its panel's note reads "Tested just now with these settings. Nothing
     is saved." The Status cell's dot follows a Test press as it follows a
     Tools press.
   - An upstream stored with transport `sse` (saved before PORM-28; the Add
     dialog no longer offers it) shows the **Unsupported** badge beside
     `MCP server` in the Kind cell, on disabled rows too, and reads `Failed` on every
     press: PoryMCP refuses that transport before it dials, so the dot is
     honest about what the proxy can do with the upstream today rather than
     about the server itself. Edit shows `sse (unsupported)` in the Transport
     select with Streamable HTTP as the only other choice, and a line under it
     naming that as the repair; saving without touching the select leaves the
     stored value alone.
   - The Add upstream dialog has a **Discover tools** button at the foot of the
     form, below the last field and above Create. It posts the form as it
     stands (nothing is saved) and renders the same panel inside the dialog,
     so a URL pointing at the base path instead of the MCP endpoint, or a token
     scoped to a read-only subset, is caught before the upstream exists. The
     button's caption says what the press does not do (“Nothing is saved, and
     this check is not recorded as a test.”), because there is no row yet to
     record it against, and an upstream that reads `Not tested` seconds after a
     green Discover would otherwise look like a bug. The dialog stays open and
     no field changes either way; a failure prints the server's own sentence in
     the panel itself, styled as a form error, and the create form's own error
     line is left alone. The button needs an `http` or `https` URL before it
     does anything, and the panel clears itself the moment it stops describing
     the form: when the URL, the transport, the auth type or the credential
     changes (the header name counts, it is part of what the call sends), and
     on Cancel, on a successful Create, and on reopening the dialog. A request
     still in flight is discarded with it, so a slow answer cannot land beside a
     URL it never asked about. There the second name on each row is a preview
     computed from the previewed slug, so it carries no Copy button: an allow
     rule written against a slug that changes at create time fails open. Which
     of the two names to use, and the fact that a previewed slug can still
     change, sit behind a “Which name do I use?” `HelpDisclosure`, closed until
     someone asks.
   - Each panel says what PoryMCP keeps, in one sentence under the summary, and
     the two surfaces say different things because they do different things. In
     the Tools dialog: “PoryMCP records when this upstream was last tested and
     whether it passed. The Status column shows it. The tool list itself is not
     stored; this is what the server said just now.” In the Add dialog,
     unchanged: “Discovered just now from the server; PoryMCP does not store
     this list.” Either sentence appears once the server has answered with a
     result, whether the upstream passed or refused, and never under an idle or
     still-running panel, or one whose request never produced a result.
   - Descriptions in either panel are clamped to three lines; one “Show full
     descriptions” button opens every row at once. If the credential would
     travel over plain `http` to something other than loopback, the panel says
     so.
   - A discovery that reached the server and failed afterwards still shows what
     it learned. The server, tool count, latency and protocol stay on screen
     above the failure sentence, because which half broke is the whole answer an
     operator is after. A server that says which era it speaks before any
     version is agreed reads "stateless, no version agreed" or "handshake, no
     version agreed".
   - Under those four, a disclosure asks "Which versions and capabilities does
     this server report?" and holds two labelled lists of zinc badges,
     Supported versions and Capabilities. A list is left out when it is empty
     and the disclosure when both are, so a server that advertised neither shows
     no empty expander. It stays on a failure too. The badges are upstream text:
     left-to-right, free to break anywhere, a real list, no `title`.
   - The panel reports what the server answered just now. A group's endpoint
     keeps its own memory of each member's era for up to ten minutes: saving the
     upstream makes the proxy ask again, and a passing test on its own does
     not. A catalogue cut short names the count it
     has (“Not every tool is listed. 40 shown. This server offers
     more.”), and never 500: the fifty-page cap and the repeated-cursor guard
     both truncate well below it.

3. **Groups**
   - List/table of groups
   - Create/Edit form with multi-select of upstreams. Edit on a row opens the
     same dialog pre-filled and saves with `PATCH /groups/{id}`, sending only
     the fields that changed; unticking and re-ticking a member is not a
     change. Unticking every member asks first through an `Alert` rendered
     inside the dialog, because every virtual key on the group loses its
     endpoints. The dialog says that adding an upstream gives every key on the
     group access to it on its next call. A `400` from the server, such as
     `unknown upstream_id: …` or `name cannot be empty`, is shown inside the
     dialog verbatim. The rules live in `web/src/lib/group-form.ts`, with tests.
   - An HTTP API upstream (PORM-146) is a member like any other, with one
     line under its row: "HTTP API. Reached at its own /api/ endpoint, not
     through the group's MCP endpoint." It is left out of the tool catalogue
     (Load tools never probes it), and when the ticked members hold no MCP
     server the tool filter's empty hint reads "The ticked upstreams are HTTP
     APIs, which have no tools to choose." The block-every-tool Alert adds
     "Its HTTP API members are not affected." when the group has one.
   - **Tool filter**, the last section of that dialog. One sentence says a rule
     names a tool as `{slug}__{tool}` on every endpoint. A radio group sets the
     mode: No filter, Allow only these tools, Deny these tools, each with what
     it does. Under a mode: the **Entries** with a badge each (`Prefix`, `Any
     member` for an unscoped entry, amber `Not advertised`, pink `Cannot be
     saved` with the reason), two inputs that add a tool or a prefix by hand
     (Enter adds the entry and does not save the dialog), and the **Load
     tools** press. The two inputs look alike and add different rules, so each
     says under its label what it adds: one tool, or every tool whose name
     starts with the text. Once every member has answered, a `Prefix` row names
     the advertised tools it matches, so a prefix typed where a tool name was
     meant shows two names and not one. Loading lists each ticked member's tools in its own block,
     two members at a time; a member that fails has its own line and **Try
     again**, a `429` stops the rest and is never retried automatically, and
     nothing loads until the press, and one load runs at a time. Past twenty
     loaded tools a **Find a tool** input narrows the rows. A tick writes the
     scoped name. A row that a
     prefix or an unscoped entry already names is drawn ticked and disabled and
     says which entry covers it; it is changed from the Entries list. Each
     member has one checkbox, worded from the mode, that writes the `{slug}__`
     prefix: every tool on that member, including ones it adds later. A tool
     whose name holds a space has no box and says that a prefix can still reach
     it. `Not advertised` and the "blocks every tool" confirm appear only when
     every member answered with its whole catalogue; otherwise one line names
     the members that did not. A stored filter the proxy cannot read is shown as
     text with the sentence that every tool is blocked, and **Replace filter**;
     other edits save without touching it. An allow rule that admits nothing
     says so. Save sends `tool_filter` only when its meaning changed, `null`
     for No filter, and refuses when the stored filter changed since the dialog
     opened. The table's Name cell shows `Allow filter`, `Deny filter` or a
     pink `Filter unreadable`. The rules live in `web/src/lib/tool-filter.ts`,
     `tool-entry.ts` and `catalogue.ts`, with tests.
   - Delete asks through `Alert`; a `409` (still targeted by a key) keeps it
     open with the reason.

4. **Virtual keys**
   - Table: Name | Key (truncated + copy) | Target | Status | Last Used | Actions.
     Under the target, a key with rules shows `3 allowed, 2 denied`, and a key
     whose stored lists cannot be read shows a pink `Rules unreadable`; a key
     whose stored `http_methods` cannot be read shows a pink `Methods
     unreadable` (PORM-146). The Endpoint column's first line is `proxy_url`,
     or the first HTTP API endpoint when the key has no MCP endpoint, and its
     second line counts the rest by kind (`+2 per-server`, `+1 HTTP API`).
   - **Allowed methods** (PORM-146), a fieldset after Rate limit and before
     Tool rules, rendered only when the target has an HTTP API among its
     members (enabled or not): "Leave all unticked to allow every method. Tick
     GET and HEAD for a read-only key. Any other method is refused with
     403." (a group target adds "Applies to the HTTP APIs in this group.")
     and six checkboxes, `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, in
     the order the server stores. Hidden, the value is never sent; shown, it
     is sent only when the set changed. On a key whose stored methods cannot
     be read, the fieldset follows the Replace pattern: one announced line
     ("This key's allowed methods cannot be read, so every request on its
     /api/ endpoint is refused."), "Saving other changes leaves them as they
     are." and a **Replace the stored methods** button, before which nothing
     is sent. Tool rules are hidden when the target has no MCP server (a
     single HTTP API, or a group of HTTP APIs); on a mixed group they apply to
     the MCP members and the picker lists those only.
   - “Create virtual key” modal/form (name, target type, target select, optional rate limit / expiry)
   - **Edit** on a row opens the same dialog on that key: name, rate limit and
     the tool rules. The target is fixed there and named under the title;
     expiry is PORM-3. It saves with `PATCH /virtual-keys/{id}`, sending only
     what changed, and shows a `400` inside the dialog verbatim.
   - **Tool rules**, on create and edit: the order the rules run in, then a
     **Deny list** and an **Allow list**, each with its entries and an input
     that adds one by hand, then one Load tools press and one picker for the
     target (the picker described under Groups, without prefixes or the
     whole-member checkbox). A radio above the picker says which list a tick
     writes to, and the rows show that list's ticks; each member's state, a
     failure with **Try again** included, is on screen as soon as the load
     settles. A tick writes the scoped name on a group target and on a single
     upstream alike. On create, choosing another target clears both lists. An
     allow entry the deny list also names carries an amber `Also denied` badge
     and "Deny wins, so it stays blocked.", and when nothing on the allow list
     can get through, one pink line says the key can call nothing; both are
     read off the two lists alone, need no loaded tools, and never hold Save
     back. For a key on a group the section opens with what the group already
     does, read-only: its mode and entries, that it has no filter, or that its
     filter cannot be read and blocks everything. In the picker a tool the
     group's filter stops says so, and while ticks go to the allow list so does
     a tool the deny list names. A key whose
     stored lists cannot be read shows one line and **Replace the stored
     rules**; until that press no list is sent, so a rename still saves. After
     it the dialog says that a list which could not be read is shown empty, since
     the API reports that one did not decode and not which. The
     rules live in `web/src/lib/virtual-key-form.ts`, with tests.
   - The one-time key dialog lists **every endpoint** the key reaches: one per
     enabled group member (`/{virtual_key_id}/{upstream_slug}/mcp`), or the
     single `proxy_url` for an upstream target. The install snippet is generated
     for all of them at once (N servers for an N-member group), with a “One
     combined server” option that emits the aggregate URL instead. The two
     options are “Separate servers” and “One combined server”, and each carries
     one plain sentence, counted and named from the key's own members:
     “Recommended. Your client sees 2 servers, GitHub and Linear, each with its
     own tools.” The rest (what a server entry is, that a client can switch one
     off on its own, the renaming rule shown with the key's own first member
     (`search` on GitHub becomes `github__search`), and that the snippet follows
     the choice) sits under the radio group in a “What's the difference?”
     `HelpDisclosure`, closed until someone asks for it. It opens on click only:
     nothing about the connection shapes appears on hover or on focus. Server
     names default to the upstream
     slug, so two keys over the same group installed in one client collide on
     server names; rename one.
   - HTTP API endpoints (PORM-146) are listed in that dialog under their own

## Untrusted text

Upstream-controlled strings (`error_message`, `params`, tool names and
descriptions, a discovered server's name and version) are rendered as React
text children, never as HTML. `dangerouslySetInnerHTML` is forbidden in
`web/src` (`react/no-danger` and `TestNoDangerouslySetInnerHTML`). Control
characters never reach the page either: discovery scrubs them out of every
upstream string it carries before clamping it (newline and tab to a space,
other C0 characters, `DEL` and U+FFFD dropped), while invisible and
bidirectional runs are still PORM-83's to deal with.

Tool descriptions are markdown by convention on the wire and are **not**
rendered as markdown here: rendering it would mean a sanitiser, which is a
dependency and a CVE surface for something nobody has asked for. They are
plain text, `dir="ltr"` so a name containing a bidi override cannot reorder
the UI around it, clamped with CSS rather than cut with `slice()` (the full
string is one press away, because reading it is the point), and never a
`title=` tooltip or a link. Do not reintroduce a remote font or
stylesheet import: the CSP will block anything that is not `'self'` (Inter
still loads from `rsms.me` until PORM-43). Headless UI may set `style`
attributes; that is allowed via `style-src-attr`, not via `'unsafe-inline'`
on `script-src`.

Dashboard `next dev` on port 3000 is served by Next, not Go, so the CSP on
the API process does not apply to that page. `NEXT_PUBLIC_API_URL` plus
`dashboardCORS` remain the local-dev path. `next dev` binds every interface
by default, so on a network you do not trust start it with `-H 127.0.0.1`
(`cd web && npx next dev -H 127.0.0.1`) so only this machine can reach port
3000.
