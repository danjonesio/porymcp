# Dashboard UI guidelines

**Branding note:** Use soft digital blues, cyans, and light polygon-inspired accents inspired by Porygon.

## Component set

The dashboard components in `web/src/components/` are PoryMCP's own MIT code
over Headless UI 2.x and Tailwind v4. Nothing in that directory comes from a
kit, and a new component is written here, never imported from one. Third-party
notices for the packages the bundle is built from are in [`NOTICE`](../NOTICE).

- **`primitives.tsx`** is the only home of the shared recipes: `focusRing`
  (the keyboard focus outline), `controlFrame` and `controlField` (the chrome
  of a text control), `optionField` (the checkbox/radio row grid) and
  `TouchTarget` (the 44px hit area). A component composes these by name; none
  carries a private copy.
- **`--color-focus`** in `web/src/styles/tailwind.css` is the one spelling of
  the focus colour (`outline-focus`, `ring-focus`, `bg-focus`). Brand surfaces
  keep literal `cyan-*` until PORM-9 moves them onto `--color-brand*`.
- The **authoritative export list** is `grep '^export' web/src/components/*.tsx`;
  it is not transcribed here.
- The **`data-slot` vocabulary** is public API: `icon` (Heroicons emit it
  themselves; parents size and colour icons off it), `control`, `label`,
  `description`, `legend`, `text`, `field`, `section`. Every Heroicon
  rendered *inside* a component is sized explicitly: by its own class, or,
  for the drawer's open/close glyphs, by `NavbarItem`'s `data-slot=icon` rule,
  exactly as the pages' icons are.
- **`--gutter`** is a cross-component contract: pages set it on `Table`
  (negative outer margin, inner padding, and the first/last cell padding below
  `sm`); `Dialog` sets its own on its panel.
- `help-disclosure.tsx` is the worked example of the house pattern: a plain
  exported function, `clsx` with the caller's `className` first, Headless UI
  for behaviour, a Heroicon for the glyph, `dark:` pairs inline.
- Dark mode follows `prefers-color-scheme`; there is no toggle.
- Behaviours that are invisible at the call site and must survive any rewrite:
  `Link` wraps `next/link` in Headless `DataInteractive` (the source of
  `data-focus` on anchors); `SidebarItem` with `href` is a Headless
  `CloseButton` (what closes the mobile drawer on navigate);
  `SidebarSection` scopes the current-page indicator in a `LayoutGroup`
  keyed on `useId()` because the sidebar is mounted twice below `lg`; a linked
  `TableRow` has exactly one tab stop.
- Known accessibility gaps carried over from the original set, tracked in
  PORM-123 together with
  the deferred improvements (`prefers-reduced-motion`, 48px touch targets):
  linked table rows have no accessible name, Logs rows are not
  keyboard-reachable, `Input`/`Textarea` show no focus outline below `sm`,
  nav items set `data-current` but not `aria-current`, and the mobile drawer
  has no accessible name.

Use the **Application Shell** (sidebar layout) as the main frame.

No dashboard route may end in `/mcp` at any depth: the proxy owns
`/{virtual_key_id}/mcp` and `/{virtual_key_id}/{upstream_slug}/mcp`, and any
path of that shape reaches it rather than the SPA.

## Pages
1. **Dashboard / Overview**
   - Stats cards (active virtual keys, total calls today, upstreams, error rate).
     Each card shows `LOADING` from `web/src/lib/placeholder.ts` (a non-breaking
     space, so the card keeps its height) until `/stats` answers. Table cells
     elsewhere show `ABSENT` (`None`) for a value the row will never have.
   - A credential notice above the stats, driven by the live counts on
     `/stats` (never by `/health`, whose verdict is a boot fact): when stored
     credentials cannot be read with the current `ENCRYPTION_KEY` it names the
     count and the fix and links to Upstreams; when a rotation is unfinished
     (`upstreams_under_previous_key > 0`) it says to run `porymcp rekey`.
     Nothing renders while stats are loading, and no server string is rendered:
     the copy is the dashboard's own. A second notice sharing this card
     recipe should extract a component rather than copy it again.
   - Recent activity feed

2. **Upstreams**
   - Table: Name | Slug | URL | Transport | Auth | Status | Actions (Tools,
     Edit, Delete). The Status cell holds two facts, stacked: the Enabled/Disabled
     badge someone set, and under it the last test as a dot and a word:
     `Not tested`, `Passed 3m ago`, `Failed 2h ago`.
   - The Auth cell says what the stored credential is worth (`auth_status`,
     PORM-52): the auth type, then `· set` when PoryMCP can use it, a pink
     `Unreadable` badge when no configured key opens it (the encryption key
     changed, so the fix is a key), a pink `Incomplete` badge when the stored
     value is empty or unusable for its auth type (the fix is the credential),
     and nothing for `none`. The rule lives in `web/src/lib/upstream-auth.ts`;
     an `auth_status` value the dashboard does not know renders no badge. So a
     `Failed` dot in the Status cell has its cause one column to the left.
   - “Add Upstream” button opens a modal or slide-over form. The Slug field previews
     what the server will derive from the Name and stays in sync until you edit
     it; leave it alone and the server derives, de-duplicates and skips reserved
     words.
   - The slug is fixed once the upstream is created, so it is not editable: it
     is the path segment of every per-member client URL and half of every tool
     identity written against that upstream. The field's help text says so:
     “Used in URLs and in tool names on the group endpoint. Fixed once the
     upstream is created.”
   - Edit on a row opens the same dialog pre-filled from the row and saves with
     `PATCH /upstreams/{id}`. The body carries only the fields that changed:
     never `slug` (the dialog shows it in its description line and has no
     input for it), and never `auth_config` unless a credential was typed. The
     credential boxes start empty and blank means keep. When the stored
     credential reads, the help text names the header it sends; when it does
     not (`Unreadable`, `Incomplete`) the help text says it has to be entered
     again, header name included. A change of auth type, or of the header name
     on a header-shaped type, makes the credential required, because the name
     is sealed inside it; the header name itself is required whenever a
     credential is being sent, so an empty one never reaches the server.
     Choosing None says the stored credential stays until a new one replaces
     it. A changed URL on a working credential says PoryMCP will send that
     credential to the new address. The Discover tools block is create-only:
     from an edit the payload route would probe with whatever the box holds,
     and Tools on the row tests the saved upstream with its stored credential.
     The row is replaced from the PATCH response, which already carries the
     reset last test, so no second request runs.
   - Delete asks through `Alert`, the shape the Virtual keys page uses. A `409`
     (still held by a group or targeted by a key) keeps the Alert open with the
     reason; a `404` reloads the list. The rules behind the dialog live in
     `web/src/lib/upstream-form.ts` and `web/src/lib/edit-error.ts`, with tests.
   - The URL field carries no help text of its own; under it sits one line,
     “What URL should I use?”, a `HelpDisclosure` that opens on click, Enter or
     Space and on nothing else. It answers in three paragraphs: **the MCP
     endpoint, not the home page** (the address usually ends in `/mcp`); **the
     final address**: PoryMCP sends the credential to exactly the URL you enter
     and never follows a redirect, so an `http://` address that redirects to
     `https://`, or a path missing its trailing slash, fails with `502` and a
     log entry reading “upstream redirected to …”; and **check it before you
     save**: Discover tools connects with these settings and lists what the
     server offers.
   - Each row has a **Tools** action next to Delete. It opens a “Tools” dialog
     that calls the upstream there and then and lists what it offers: server
     name and version, latency, the protocol it negotiated, the tool count, and
     every tool by the name the server publishes and, beneath it, by the name a
     group endpoint gives it (`{slug}__{tool}`), with a Copy button that copies
     that second form, the one an allow rule has to be written in. A Refresh
     button re-runs it. The tool list is not stored and is gone when the dialog
     closes, but the run itself is: every press records, on the upstream's row,
     when it ran and whether it passed, and the panel says so. The Status cell
     in the table carries that result (a dot and a word under the Enabled
     badge: `Not tested`, `Passed 3m ago`, `Failed 2h ago`), so a misconfigured
     upstream is visible without opening the dialog. The press updates the row
     itself: the table is re-read when the run settles, so the dot changes
     without a reload even if the dialog was closed while the handshake was
     still running, and it reads `Passed just now` or `Failed just now` for the
     first minute. The relative label is computed when the list arrives rather
     than on a timer, so it does not tick on a page left open; the exact instant
     is in the cell's `<time>`. Changing an upstream's URL, transport, auth type
     or credential resets it to `Not tested`: a green dot against a connection
     nobody has tried is worse than no dot. The row is not clickable and does
     not expand: discovery is an authenticated outbound call to an
     operator-supplied URL, and now also a write to that upstream's row, so it
     happens only on a deliberate press.
   - An upstream whose transport is `sse` reads `Failed` on every press until
     PORM-28 lands: PoryMCP refuses that transport before it dials, so the dot
     is honest about what the proxy can do with the upstream today rather than
     about the server itself.
   - The Add upstream dialog has a **Discover tools** button at the foot of the
     form, below the last field and above Create. It posts the form as it
     stands (nothing is saved) and renders the same panel inside the dialog,
     so a URL pointing at the base path instead of the MCP endpoint, or a token
     scoped to a read-only subset, is caught before the upstream exists. The
     button's caption says what the press does not do (“Nothing is saved, and
     this check is not recorded as a test.”), because there is no row yet to
     record it against, and an upstream that reads `Not tested` seconds after a
     green Discover would otherwise look like a bug. The dialog stays open and
     no field changes either way; a failure prints the server's own sentence in
     the panel itself, styled as a form error, and the create form's own error
     line is left alone. The button needs an `http` or `https` URL before it
     does anything, and the panel clears itself the moment it stops describing
     the form: when the URL, the transport, the auth type or the credential
     changes (the header name counts, it is part of what the call sends), and
     on Cancel, on a successful Create, and on reopening the dialog. A request
     still in flight is discarded with it, so a slow answer cannot land beside a
     URL it never asked about. There the second name on each row is a preview
     computed from the previewed slug, so it carries no Copy button: an allow
     rule written against a slug that changes at create time fails open. Which
     of the two names to use, and the fact that a previewed slug can still
     change, sit behind a “Which name do I use?” `HelpDisclosure`, closed until
     someone asks.
   - Each panel says what PoryMCP keeps, in one sentence under the summary, and
     the two surfaces say different things because they do different things. In
     the Tools dialog: “PoryMCP records when this upstream was last tested and
     whether it passed. The Status column shows it. The tool list itself is not
     stored; this is what the server said just now.” In the Add dialog,
     unchanged: “Discovered just now from the server; PoryMCP does not store
     this list.” Either sentence appears once the server has answered with a
     result, whether the upstream passed or refused, and never under an idle or
     still-running panel, or one whose request never produced a result.
   - Descriptions in either panel are clamped to three lines; one “Show full
     descriptions” button opens every row at once. If the credential would
     travel over plain `http` to something other than loopback, the panel says
     so.
   - A discovery that got through the handshake and failed afterwards still
     shows what it learned. The server, tool count, latency and protocol stay on
     screen above the failure sentence, because which half broke is the whole
     answer an operator is after. A catalogue cut short names the count it
     has (“Not every tool is listed. 40 shown. This server offers
     more.”), and never 500: the fifty-page cap and the repeated-cursor guard
     both truncate well below it.

3. **Groups**
   - List/table of groups
   - Create/Edit form with multi-select of upstreams. Edit on a row opens the
     same dialog pre-filled and saves with `PATCH /groups/{id}`, sending only
     the fields that changed; unticking and re-ticking a member is not a
     change. Unticking every member asks first through an `Alert` rendered
     inside the dialog, because every virtual key on the group loses its
     endpoints. The dialog says that adding an upstream gives every key on the
     group access to it on its next call. A `400` from the server, such as
     `unknown upstream_id: …` or `name cannot be empty`, is shown inside the
     dialog verbatim. The rules live in `web/src/lib/group-form.ts`, with tests.
   - Delete asks through `Alert`; a `409` (still targeted by a key) keeps it
     open with the reason.

4. **Virtual keys**
   - Table: Name | Key (truncated + copy) | Target | Status | Last Used | Actions
   - “Create virtual key” modal/form (name, target type, target select, optional rate limit / expiry)
   - The one-time key dialog lists **every endpoint** the key reaches: one per
     enabled group member (`/{virtual_key_id}/{upstream_slug}/mcp`), or the
     single `proxy_url` for an upstream target. The install snippet is generated
     for all of them at once (N servers for an N-member group), with a “One
     combined server” option that emits the aggregate URL instead. The two
     options are “Separate servers” and “One combined server”, and each carries
     one plain sentence, counted and named from the key's own members:
     “Recommended. Your client sees 2 servers, GitHub and Linear, each with its
     own tools.” The rest (what a server entry is, that a client can switch one
     off on its own, the renaming rule shown with the key's own first member
     (`search` on GitHub becomes `github__search`), and that the snippet follows
     the choice) sits under the radio group in a “What's the difference?”
     `HelpDisclosure`, closed until someone asks for it. It opens on click only:
     nothing about the connection shapes appears on hover or on focus. Server
     names default to the upstream
     slug, so two keys over the same group installed in one client collide on
     server names; rename one.
   - Rotate / Revoke / Delete actions

5. **Logs**
   - Two sections under one heading, “Proxy calls” and “Admin activity”, each
     with its own filter, fetch, error line and empty copy. Neither table
     renders until its first fetch settles, so the empty copy cannot flash on
     first paint.
   - Proxy calls: filterable table (virtual key, method, tool, status), newest
     50 first: Time | Virtual key | Method | Tool | Status | Latency, with the
     status as a badge: lime for `success`, amber for `blocked`, pink for
     `error`. The four filters govern this table only.
   - A proxy row is clickable, not expandable: it opens a “Log detail” dialog
     holding the request id, the upstream, the error message when there is
     one, and the params as pretty-printed JSON.
   - Admin activity: the 50 most recent management-plane changes, newest
     first, with one Resource select (all, upstreams, groups, virtual keys):
     Time | Event | Details | From. Event is one sentence (“Rotated virtual key
     demo-vk”); Details lists the changed field names and the bounded values
     the server records, `None` when there is nothing to say; From is
     `remote_addr` verbatim, so the literal `unknown` is a value the row has
     and is never swapped for `None`. `details` is drawn by named key and never
     as JSON; an unknown key renders by name only. Rows are not interactive,
     so the table adds no keyboard gap. Empty copy: “No changes recorded yet.”
     or, with a filter set, “No matching changes.” `actor` is not a column
     while every row says `admin`. The sentence and field rules live in
     `web/src/lib/admin-event.ts` with their tests beside it.

6. **Settings** (basic)
   - Admin key management, retention settings, etc.

## Components available
- Application shell + sidebar (`sidebar-layout`, `sidebar`, `navbar`)
- Tables (`table`)
- Forms (`fieldset`, `input`, `textarea`, `select`, `checkbox`, `radio`)
- Modals (`dialog`, `alert`), disclosures (`help-disclosure`)
- Stats cards (`app/stat.tsx`)
- Badges (`badge`), buttons (`button`), text (`text`, `heading`, `divider`, `description-list`)
- Menus (`dropdown`), links (`link`), the sign-in frame (`auth-layout`)

Keep new pages consistent with the existing set.  
Support light + dark if easy.

## Untrusted text

Upstream-controlled strings (`error_message`, `params`, tool names and
descriptions, a discovered server's name and version) are rendered as React
text children, never as HTML. `dangerouslySetInnerHTML` is forbidden in
`web/src` (`react/no-danger` and `TestNoDangerouslySetInnerHTML`). Control
characters never reach the page either: discovery scrubs them out of every
upstream string it carries before clamping it (newline and tab to a space,
other C0 characters, `DEL` and U+FFFD dropped), while invisible and
bidirectional runs are still PORM-83's to deal with.

Tool descriptions are markdown by convention on the wire and are **not**
rendered as markdown here: rendering it would mean a sanitiser, which is a
dependency and a CVE surface for something nobody has asked for. They are
plain text, `dir="ltr"` so a name containing a bidi override cannot reorder
the UI around it, clamped with CSS rather than cut with `slice()` (the full
string is one press away, because reading it is the point), and never a
`title=` tooltip or a link. Do not reintroduce a remote font or
stylesheet import: the CSP will block anything that is not `'self'` (Inter
still loads from `rsms.me` until PORM-43). Headless UI may set `style`
attributes; that is allowed via `style-src-attr`, not via `'unsafe-inline'`
on `script-src`.

Dashboard `next dev` on port 3000 is served by Next, not Go, so the CSP on
the API process does not apply to that page. `NEXT_PUBLIC_API_URL` plus
`dashboardCORS` remain the local-dev path. `next dev` binds every interface
by default, so on a network you do not trust start it with `-H 127.0.0.1`
(`cd web && npx next dev -H 127.0.0.1`) so only this machine can reach port
3000.
